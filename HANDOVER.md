## Rules that must not be broken

1. **Do NOT override** `Search`, `PageTitle`, `Banner`, `ThemeSelect` in the
   Starlight config — `starlight-versions` owns them; overriding warns + breaks
   versioning. Safe to override: `SiteTitle`, `Footer`, others.
2. **Snapshot ordering (critical):** to freeze a version without a not-yet-shipped
   feature — (a) author current docs WITHOUT the feature, (b) add the version to
   `versions[]` in `astro.config.mjs` and run a build so it snapshots into
   `src/content/docs/<slug>/`, (c) THEN add the feature to current. The plugin
   copies current → snapshot only if the folder doesn't exist yet.
3. Keep `src/config/features.ts` the single source of truth: the matrix and the
   search hint both read it. Update it when adding/deprecating a feature.
4. A new feature page needs: frontmatter (`since`/`tier`), `<FeatureMeta>`, the
   Intro → Explanation → Types → Code → `<GridDemo>` template, AND an entry in
   `src/config/features.ts`.
5. **Framework code samples.** Use Starlight's built-in `<Tabs syncKey="framework">`
   with a `<TabItem label="JavaScript">` / `<TabItem label="Angular">` per code
   fence (`import { Tabs, TabItem } from '@astrojs/starlight/components'`). The
   shared `syncKey="framework"` keeps every tab group on a page in sync and
   persists the reader's choice across navigation — no custom JS/CSS. Keep the
   `label` values identical across pages so they stay synced. Exemplar:
   `virtual-scrolling.mdx`.

## ZenGrid library DX recommendations (fix in `@zengrid/core`)

Surfaced while integrating the grid into `GridDemo`:

- Export a typed `ColumnDef<T>` generic — currently columns need `as any`.
- Add a package `exports` entry for the stylesheet (e.g. `@zengrid/core/styles`)
  instead of the deep `@zengrid/core/dist/styles.css` path.
- Expose the scroll viewport element (e.g. `grid.viewportEl`) — demos currently
  find it via an overflow heuristic.
- Stabilize class hooks (`.zg-cell`, header cell classes) across versions.

Surfaced while authoring the `@zengrid/angular` code sample (framework switcher):

- `<zen-grid [data]>` is typed `any[][]` — a positional 2-D cell array, not
  typed row objects keyed by `ColumnDef.field`. Docs samples read awkwardly and
  lose type safety; consider accepting `T[]` rows resolved through the columns.
- `<zen-grid>` requires both `[rowCount]` and `[colCount]` even when `[columns]`
  and `[data]` are supplied — the counts are derivable. Make them optional/inferred
  so the minimal example is just columns + data.

## Done

- **Framework code samples via native Starlight `<Tabs>`.** Replaced the earlier
  custom sidebar dropdown (inline head script + `data-framework` on `<html>` +
  `<Fw>` wrapper + `docs-enhance.js` handler + custom pill CSS) — that approach
  caused the reported bugs: a post-paint flash of the relocated version switcher,
  a double chevron, and unreliable code swapping. Now each framework sample is a
  `<TabItem label="…">` inside `<Tabs syncKey="framework">` (Starlight's built-in
  component). It renders server-side (no flash), is theme-styled, syncs every tab
  group on a page, and persists the reader's choice across navigation with zero
  custom JS/CSS. Deleted `src/components/docs/Fw.astro`, `src/config/frameworks.ts`,
  the `frameworkHeadScript` in `astro.config.mjs`, the framework switcher block in
  `public/docs-enhance.js`, and the `.zg-*switcher` / `.zg-fw-variant` CSS. The
  version switcher stays in the header where the `starlight-versions` plugin
  renders it (no relocation) — single native chevron, no flash. Verified in a
  headless Chrome run: tabs render (JavaScript/Angular), JS→Angular swaps the code,
  version switcher lives only in the header on desktop (the sidebar copy is the
  plugin's `md:sl-hidden` mobile-menu duplicate), zero console errors. Exemplar
  wired on `virtual-scrolling.mdx` (Angular sample uses the real `@zengrid/angular`
  `<zen-grid>` API). Build is green.
- **Full brand-token bridge in `src/styles/docs.css`.** Root cause of the
  "looks like a different site" chrome: only the accent + font were mapped, so
  Starlight's gray ramp (and every surface derived from it — page bg, nav,
  sidebar, hairlines, inline-code, body text) stayed default. Now the whole
  `--sl-color-gray-1..6` + `black`/`white` ramp is remapped to the warm brand
  neutrals per theme, headings use the Manrope display face, and the default
  `:root` theme was flipped from light→dark to match Starlight's own convention
  (the old `:root,:root[data-theme="light"]` grouping mismatched Starlight's
  dark-default root). Footer, version dropdown, and sidebar now inherit brand
  colors automatically.
- **Design-system pass on the docs** (matches `design-ref/…/CLAUDE.md` +
  `ZenGrid Docs.dc.html`). `astro.config.mjs` sets a custom Expressive Code
  theme `zengridInk` — always-dark warm ink slab (`#1e1a15`), JetBrains Mono,
  14px radius, terminal frame, and the exact syntax triplet (violet `#c9a0e8`
  keywords / teal `#8fd6c8` strings / salmon `#f2a583` class+fn names / amber
  numbers). `src/styles/docs.css` adds Manrope-800 display headings + type
  scale, chip inline-code, coral-edged active sidebar item + mono group labels,
  surface-card callouts with accent edges, rounded prev/next cards, and pill
  search/version controls. Unverified visually (no screenshot in this env) —
  selectors follow Starlight's documented class hooks; a couple (sidebar
  `.group-label`, aside internals) may need selector tweaks against built HTML.
